# 그린 바 리팩터링

리팩터링은 **관찰 가능한 동작을 하나도 바꾸지 않으면서** 설계를 개선하는 일이다.
이 정의를 지키는 유일한 방법은 초록 바를 안전망으로 쓰는 것이다.

## 0. 먼저 창을 연다

```sh
./.claude/hooks/tdd-state.sh enter-refactor
```

이건 형식이 아니라 선언이다. "지금부터 동작을 바꾸지 않겠다"고 말했기 때문에
가드가 `src/main` 편집을 허용한다.

거부되면 이유는 셋 중 하나이고 전부 `./gradlew test` 로 풀린다:

| 거부 사유 | 뜻 |
|---|---|
| 상태가 `GREEN_VERIFIED` 가 아님 | 안전망이 없다. 초록부터 만들어라 |
| 마지막 초록 이후 `src/main` 이 변경됨 | 그 변경이 검증되지 않았다 |
| 마지막 초록이 15분보다 오래됨 | 그 사이 무엇이 바뀌었는지 알 수 없다 |

## 1. 리듬: 한 동작 → 한 실행

```
냄새를 하나 고른다
  → 리팩터링 동작을 하나 적용한다
    → ./gradlew :core:test --tests '*관련테스트'
      → 초록? 다음 냄새로
      → 빨강? 즉시 되돌린다 (디버깅하지 않는다)
```

여러 개를 몰아서 고친 뒤 실행하면, 깨졌을 때 원인도 되돌릴 단위도 사라진다.
편집 예산(기본 40회)이 소진되면 가드가 막는데, 그건
**리팩터링 단위가 너무 크다**는 신호다.

## 2. 빨개지면 되돌린다 — 고치지 않는다

리팩터링 중의 RED는 버그 리포트가 아니라 "방금 그 동작이 틀렸다"는 뜻이다.
되돌리고 더 작게 다시 하는 쪽이 언제나 빠르다.

```sh
git diff              # 방금 무엇을 했는지 본다
git checkout -- <파일> # 되돌린다
```

디버깅을 시작하는 순간 리팩터링이 아니라 동작 변경을 하고 있는 것이다.

## 3. 테스트를 고쳐야 한다면 리팩터링이 아니다

| 상황 | 판정 |
|---|---|
| 어서션을 고쳐야 통과한다 | **동작 변경.** 멈추고 새 사이클로 |
| 시그니처가 바뀌어 테스트 호출부를 고쳐야 한다 | **공개 계약 변경.** 계약을 확인하라 |
| 테스트 코드의 중복을 없앤다 | 리팩터링. 단 어서션은 건드리지 않는다 |
| 목 스텁을 새 시그니처에 맞춘다 | 경계면 위험. 실물과 대조하라 |

마지막 항목이 조용한 함정이다. 스텁을 새 시그니처에 맞추면 테스트는 초록인데
실제 호출부가 안 맞을 수 있다 — `tdd-boundary-inspector` 의 1순위 검증 항목이다.

## 4. 냄새 → 동작

| 냄새 | 동작 | 언제 |
|---|---|---|
| 긴 메서드 | 메서드 추출 | 한 화면을 넘거나 주석으로 단락을 나누고 있을 때 |
| 중복 코드 | 메서드 추출 → 공통화 | 세 번째 등장에서 (두 번은 우연일 수 있다) |
| 원시 타입 집착 | 값 객체 도입 (`Money`, `OrderId`) | 검증 규칙이 여러 곳에 흩어질 때 |
| 긴 파라미터 목록 | 파라미터 객체 도입 | 4개를 넘고 늘 함께 다닐 때 |
| 조건문 뭉치 | 다형성으로 치환 / 가드 절 | `switch`/`if-else` 가 타입에 따라 갈릴 때 |
| 기능 편애 | 메서드 이동 | 다른 객체의 데이터만 만지는 메서드 |
| 산탄총 수술 | 클래스로 모으기 | 한 변경이 여러 파일을 건드릴 때 |
| 이름이 거짓말 | 이름 변경 | 언제나. 가장 값싸고 가장 효과가 크다 |

상세와 순서: [references/refactoring-catalog.md](references/refactoring-catalog.md)

## 5. 안전한 순서

가장 안전한 것부터 한다. 실패해도 되돌리기 쉬운 순서다.

```
1. 이름 변경 (IDE 기능 사용)
2. 메서드 추출 / 인라인
3. 필드·메서드 이동
4. 값 객체 도입
5. 조건문 → 다형성
6. 클래스 분리
```

1~2는 거의 언제나 안전하다. 5~6은 사이클 하나를 통째로 쓸 만한 크기이며,
그럴 만한 값어치가 있는지 먼저 판단하라.

## 6. 언제 멈추는가

- **부채 목록을 다 처리했다** — 마감
- **테스트가 계속 빨개진다** — 되돌리고 마감. 다음 사이클로 넘긴다
- **동작을 바꿔야만 개선된다** — 리팩터링 대상이 아니다. 새 TDD 사이클로
- **예산/시간이 소진됐다** — 단위가 크다는 신호. 초록으로 마감하고 쪼갠다
- **더 나아지는지 확신이 없다** — 멈춘다. 리팩터링에도 수확 체감이 있다

마감은 언제나 **초록 확인**으로 한다:

```sh
./gradlew :core:test
```

## 7. 하지 말 것

| 금지 | 이유 |
|---|---|
| 여러 리팩터링을 몰아서 하고 한 번 실행 | 원인 분리 불가, 되돌릴 단위 소실 |
| 리팩터링하면서 기능 추가 | 둘 중 하나가 반드시 검증되지 않는다 |
| 공개 API 시그니처 변경 | 계약이다. 계약 변경은 설계 단계의 일 |
| "나중을 위한" 추상화 도입 | 쓰이지 않는 유연성은 부채다 |
| 테스트 없는 코드 리팩터링 | 안전망이 없다. 특성화 테스트를 먼저 써라 |
| 성능 최적화를 리팩터링이라 부르기 | 측정 없는 최적화는 그냥 복잡도 추가 |
